# Launching external agents

Loti can hand your terminal to a configured agent harness for an epic or ticket.
A launch gives the agent a workflow, a precise tracker target, and an initial
instruction explaining how to get started. It does **not** automatically claim a
ticket, change its status, add a comment, or track the agent after it exits.
Those actions belong in the workflow or in your normal tracker process.

## Configure profiles and workflows

An **agent profile** tells loti how to start one harness. A **workflow** is the
Markdown instruction set for a kind of work, such as implementation or review.
Keep them separately so the same workflow can run with different harnesses.

Place resources either in your XDG configuration directory, for use across
projects:

```text
$XDG_CONFIG_HOME/loti/agents/
$XDG_CONFIG_HOME/loti/workflows/
```

or configure project-local directories in the nearest `.loti.conf`:

```toml
agent-root = "agents"
workflow-root = "workflows"
```

Relative paths are relative to `.loti.conf`; both configured directories must
already exist. A local resource with the same name overrides the global resource.
That is deliberate: an invalid local override is shown as an error rather than
silently using the global file.

Resource names come from filenames. For example, `pi.toml` is the `pi` profile
and `implement.md` is the `implement` workflow. Names may contain ASCII letters,
digits, hyphens, and underscores.

### Example profile

Create `agents/pi.toml`:

```toml
command = "pi"
args = ["{{ loti_prompt }}"]

# Optional. Without this, the harness starts at the store root.
cwd = "{{ current_directory }}"

[env]
PI_SESSION_NAME = "loti-{{ loti_ref }}-{{ loti_workflow }}"
```

Loti runs the command and arguments directly, not through a shell. This keeps
spaces and quotes in generated instructions safe and predictable. Put the
`{{ loti_prompt }}` argument where your harness expects its initial prompt. It
must appear as a complete argument exactly once.

Profiles may use these placeholders in arguments, `cwd`, and environment values:

| Placeholder | Meaning |
|---|---|
| `{{ loti_prompt }}` | initial instruction generated by loti |
| `{{ project_root }}` | root of the loti store |
| `{{ current_directory }}` | directory from which you invoked loti |
| `{{ loti_ref }}` | selected epic ID or ticket reference |
| `{{ loti_ref_name }}` | selected epic or ticket name |
| `{{ loti_workflow }}` | selected workflow name |

The working directory must render to an absolute directory that exists. Profile
environment keys may not start with `LOTI_`; loti reserves that prefix for the
session context it passes to the launched agent.

### Example workflow

Create `workflows/implement.md`:

```markdown
# Implement

Read the target and its comments before changing anything. Work only within the
selected target's scope. Run the relevant tests before reporting the result.
```

Workflow Markdown is passed through unchanged. It has no required front matter
or special loti syntax.

## Inspect the available resources

```sh
loti agent list
loti agent show pi
loti workflow list
loti workflow show implement
```

Lists show whether each effective resource came from the local or global
configuration. They also show malformed files as diagnostics, so a broken
profile does not hide the rest of the catalog. `workflow show` writes the exact
Markdown that the agent will read.

## Start an agent from the CLI

Choose both a profile and a workflow explicitly:

```sh
loti agent run my-epic --agent pi --workflow implement
loti agent run my-epic/12 --agent pi --workflow implement
```

Loti checks the target, the selected resources, the rendered profile, and the
terminal before it starts the harness. The command requires stdin, stdout, and
stderr to be terminals. If preflight fails, no agent starts and no tracker data
changes.

On Unix, a successful launch replaces the `loti` process with the configured
harness. When the harness exits, its exit status is the command's exit status.

The harness receives an initial instruction that tells it to:

1. run `loti skill`;
2. read the selected workflow with `loti workflow show`; and
3. inspect the selected epic or ticket with `loti epic show` or `loti ticket show`.

It also receives `LOTI_AGENT_SESSION` and `LOTI_AGENT_WORKFLOW`. These are
cooperative guardrails: while they are present, the agent cannot use the
operator-facing `loti agent` commands and can read only its selected workflow.
They are guidance for a normal launched session, not a security boundary against
a process that intentionally changes its environment.

## Start an agent from the browser

In `loti tui`, move to an epic or ticket, press `e`, then press `w`. The picker
shows a workflow field first and an agent-profile field second. Choose a value
in each and accept the form to launch immediately; there is no extra
confirmation.

The browser validates the choice before releasing the terminal. If it cannot
launch, it keeps the picker open and explains why. Once a harness starts, the
browser temporarily gives it the terminal. When the harness exits, the browser
restores and repaints itself. A failed start or non-zero exit is then shown in
the browser.

The workflow action is not offered for comments, labels, assets, dependencies,
or other metadata rows. For the full browser key guide, see [TUI guide](tui.md);
for the complete contract, see [agent integration specification](specs/agent-integration-spec.md).
